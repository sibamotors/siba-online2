# گزارش ممیزی فنی، امنیتی و تجربهٔ کاربری سیباموتور

**تاریخ ممیزی:** ۱۶ اکتبر ۲۰۲۶  
**دامنه:** کد موجود در ZIP، تنظیمات build/اجرای Node، migrationها، ورود و نشست، توابع سرور، داشبورد/راهنما و دستورالعمل استقرار.  
**محدودیت مهم:** این ممیزی ایستا و مبتنی بر فایل‌هاست؛ به VPS واقعی، دیتابیس تولید، DNS، Nginx، لاگ‌های PM2 یا حساب کاربری وارد نشده‌ام. بنابراین نتیجهٔ واقعی استقرار و امنیت میزبان تأیید نشده است.

## جمع‌بندی مدیریتی

پروژه قابلیت‌های قابل‌توجهی فراتر از یک تختهٔ کانبان دارد: اسکرام/اسپرینت، گانت، تقویم شمسی، وابستگی کارت‌ها، پیام‌رسانی و فایل، گزارش و تأیید، مجوزهای عملیات، نشست امضاشده و لاگ ممیزی. مهم‌ترین ضعف‌ها بیشتر در **دقت و معنای شاخص‌ها، فرآیند استقرار، آزمون‌پذیری و محدودیت معماری ذخیره‌سازی** هستند تا صرفاً ظاهر صفحات.

در نسخهٔ اصلاح‌شده، شاخص از ایجاد تا ستون نهایی به‌صورت صریح و بدون فرض نادرست دربارهٔ نقطهٔ تعهد نام‌گذاری می‌شود، شاخص سن کار باز از Cycle Time متمایز شده، نرخ تکمیل ۷ و ۳۰ روز اضافه شده، نمودار رویدادها از شمارش دوبارهٔ ورود به ستون نهایی جلوگیری می‌کند، TLS دیتابیس خارجی به‌صورت پیش‌فرض گواهی را اعتبارسنجی می‌کند، start script فایل `.env` را بارگذاری و سپس migrationها را اجرا می‌کند و راهنمای اختصاصی VPS/PM2/Nginx اضافه شده است.

## نتیجهٔ بازبینی امنیتی ایستا

- بیشتر توابع داده‌ای سرور از middleware احراز هویت/نقش/مجوز استفاده می‌کنند. چهار مسیر بدون middleware عمومی شناسایی شدند: ورود با رمز، مرحلهٔ PIN، خواندن وضعیت نشست (GET)، و خروج؛ دو مسیر ورود اعتبارسنجی و محافظت CSRF دارند و خروج هم Same-Site را بررسی می‌کند. این مورد را بر اساس کد بررسی کردم، نه تست نفوذ زنده.
- کوکی نشست `HttpOnly` و در تولید `Secure` با پیشوند `__Host-` است؛ SameSite و نسخهٔ نشست نیز بررسی می‌شود. این با راهنمای [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) هم‌راستا است.
- محافظت درخواست‌های تغییردهنده از Fetch Metadata و بررسی Origin/Referer استفاده می‌کند. مطمئن شوید برنامه فقط از پشت reverse proxy قابل دسترسی است و `Host`/IPهای forwarded از شبکهٔ عمومی قابل جعل نیستند؛ الگوی fallback با توصیه‌های [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) هم‌جهت است.
- فایل‌های کاربر محدودیت اندازه دارند، نوع MIME مجاز محدود شده و دسترسی download به فرستنده/افراد مرتبط بررسی می‌شود. خروجی CSV داشبورد هم برای شروع‌های شبیه فرمول صفحه‌گسترده خنثی‌سازی انجام می‌دهد.
- در Nginx باید port برنامه فقط روی `127.0.0.1` باز باشد، PostgreSQL به اینترنت عمومی expose نشود، `.env` دسترسی `600` داشته باشد و HTTPS معتبر برقرار شود. HSTS با `includeSubDomains` تنها وقتی مناسب است که همهٔ زیردامنه‌ها نیز HTTPS داشته باشند.

## نتایج آزمون در محیط فعلی

- **موفق:** `npm test` — ۲۳ تست (۷ تست migration-plan، ۴ تنظیم SSL، ۳ تست lifecycle استقرار، ۹ تاریخ شمسی/شاخص‌های کانبان) پاس شدند.
- **موفق:** بررسی syntax اسکریپت‌های `.mjs`، فایل `ecosystem.config.cjs` و parse فایل `package.json`.
- **قابل تأیید نبود:** `npm run typecheck` به‌علت نبودن type definitions برای `node` و `vite/client` متوقف شد؛ `npm run lint` نیز به‌دلیل نبودن executable مربوط به ESLint اجرا نشد. نصب کامل وابستگی‌ها در این محیط به پایان نرسید.
- **Build:** `npm run build` اجرا شد اما پیش از build به خطای `vite: not found` رسید؛ بنابراین build موفق را تأیید نمی‌کنم.
- **اجرا نشده/قابل تأیید نبود:** `npm audit`، تست مرورگر با Playwright، آزمون بار، و بررسی config واقعی PM2/Nginx/DB روی VPS. بنابراین این گزارش ادعای «تست production موفق» نمی‌کند.

## چک‌لیست پیش از اعمال روی VPS

1. بکاپ قابل بازیابی از دیتابیس و خروجی فضای کاری تهیه کن.
2. ZIP جدید را در مسیر موقت extract کن؛ `.env`، بکاپ‌ها و لاگ‌های سرور را با فایل‌های ZIP جایگزین نکن.
3. روی نسخهٔ جدید `npm ci`, `npm run typecheck`, `npm run lint`, `npm test` و `npm run build` را اجرا کن؛ هیچ‌کدام را با شکست رد نکن.
4. `DATABASE_URL`, `SESSION_SECRET`, TLS و مجوز `.env` را بررسی کن.
5. با `pm2 start ecosystem.config.cjs` یا بعد از deploy با `pm2 restart ecosystem.config.cjs --update-env` اجرا کن؛ `pm2 startup` و `pm2 save` را طبق خروجی واقعی PM2 انجام بده.
6. `/login`، ورود/خروج، تغییر رمز اجباری، ساخت/انتقال کارت، پیام و پیوست، گزارش، مجوزهای کاربر عادی، نمودار اسکرام و بازیابی بکاپ را دستی تست کن.

## پیشنهادهای مرحلهٔ بعد

1. **پیش از انتشار:** build/typecheck/lint روی ماشین دارای dependency کامل، audit خودکار npm در CI و smoke test روی staging.
2. **کیفیت محصول:** تست E2E نقش‌های ادمین/کاربر، تست دسترس‌پذیری WCAG 2.2 برای کنتراست/focus/keyboard، و تست‌های امنیتی برای مجوز دسترسی به گزارش/پیوست/گروه.
3. **شاخص‌های قابل اتکا:** ذخیرهٔ تاریخچهٔ انتقال بین ستون‌ها و شروع کار به‌صورت event record؛ سپس Cycle Time واقعی، throughput تاریخی شامل کارهای بازگشایی‌شده و نمودار Cumulative Flow قابل محاسبه خواهد بود.
4. **اسکرام:** snapshot روزانه با زمان‌بند سرور و منطقهٔ زمانی مشخص، نه صرفاً بازدید کاربر از صفحه.
5. **مقیاس و تاب‌آوری:** نرمال‌سازی workspace در PostgreSQL، تراکنش‌های write و concurrency test؛ تنها بعد از آن چند instance یا cluster فعال شود.
6. **زیرساخت وابستگی‌ها:** بررسی برنامه‌ریزی‌شده برای خروج از Nitro 3 beta یا به‌روزرسانی کنترل‌شده به آخرین patch سازگار، با build/test قبل و بعد از تغییر.
